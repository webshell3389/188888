## 1. 执行摘要

服务在低负载（`/beacon` 仅 25–30 次/分钟）下持续占满 2 个 CPU 核，`/beacon` 成功率 **0%**。

这不是容量不足，而是**应用层存在结构性缺陷**：`registerC2` 每次请求调用
`CommandQueue.expandCands` → `ListDevices()`，该函数存在 **N+1 查询**且在**无任何并发上限**的情况下被并发调用。
实测在途请求堆积至 **76 个 goroutine 同时卡在同一条调用链**，GC 被强制连续执行 3 分钟无法完成，
形成"请求越多 → 越慢 → 堆积越多"的正反馈死亡螺旋。

**已完成的止血措施缓解了内存与磁盘压力，但未能解决 CPU 打满。** 详见 §5。

## 3. 根因分析

### 3.1 已被证伪的假设

| 假设 | 证伪依据 |
|---|---|
| 内存泄漏 / OOM | `dmesg` 无 OOM 记录；MemAvailable 10.5 GB；RSS 1.7 GB→73 MB（单进程后） |
| 磁盘写满 | 根分区 24% 使用率，剩余 56 GB |
| 流量洪峰 | `/beacon` 仅 25–30 次/分钟（0.45 req/s） |
| 网络 / Cloudflare | `/event` 走同一链路 **100% 返回 200** |
| 跨进程 SQLite 锁竞争 | 单进程下 CPU 仍 186%（E2） |
| SQLite 索引损坏 | `PRAGMA quick_check` → `ok`；`EXPLAIN QUERY PLAN` 显示索引正常命中 |
| N+1 × 设备数是主因 | 裁剪到 200 台后 CPU 无变化（E3） |
| 进程崩溃重启 | `NRestarts=0`（诊断前），自 21:10 持续运行 |

### 3.2 决定性证据：goroutine 栈

**第一次 dump**（`kill -QUIT`，01:07:17）——定位到 SQLite 索引遍历：

```
goroutine 1030 [running]:
  modernc.org/sqlite/lib._btreeParseCellPtrIndex(...)          ← 正在解析索引 B-tree 单元
  ... _sqlite3VdbeStep → Xsqlite3_step
  modernc.org/sqlite.(*rows).Next()
  mockc2/internal/store.scanRows          (db.go:148)
  mockc2/internal/store.(*DB).Query       (db.go:130)
  mockc2/internal/store.ClientStageProgress (stage_progress.go:70)
  mockc2/internal/store.ListDevices()     (panel_query.go:77)   ← ★
  mockc2/internal/store.(*CommandQueue).expandCands  (command_queue.go:212)
  mockc2/internal/store.(*CommandQueue).TakeFor       (command_queue.go:148)
  mockc2/internal/server.registerC2.func1 (sync.go:74)          ← 入口
```

同帧附带：`goroutine 2 [force gc (idle), 1 minutes]` —— 强制 GC 连续执行 1 分钟。

**第二次 dump**（01:10，裁剪设备表之后）——**这才是根因所在**：

```

     75 [select]
      1 [force gc (idle), 3 minutes]
      1 [finalizer wait, 3 minutes]
      1 [cleanup wait, 3 minutes]

=== 出现频次最高的调用链（76 个 goroutine 命中同一条链）===
    76 × mockc2/internal/server.registerC2            (sync.go)
    76 × mockc2/internal/store.(*CommandQueue).TakeFor (command_queue.go)
    76 × mockc2/internal/store.(*CommandQueue).expandCands (command_queue.go)
    76 × mockc2/internal/store.ListDevices()          (panel_query.go)
    76 × mockc2/internal/store.(*DB).Query            (db.go)
    37 × mockc2/internal/store.(*DB).QueryOne         (db.go)   ← 额外 N+1
    29 × mockc2/internal/store.Profile                ← 额外 N+1
    19 × mockc2/internal/store.walletsMeta            ← 额外 N+1
```

**关键读数：`ListDevices()` 被 76 个 goroutine 同时调用。**

### 3.3 死亡螺旋机制

```
1. registerC2 每次请求无条件调用 TakeFor → expandCands → ListDevices()
   └─ ListDevices 内含 N+1：每台设备额外 1+ 次 QueryOne / Profile / walletsMeta
      实测：1956 台设备 → 单次请求约 20 秒（与观察到的 60s nginx 超时吻合）

2. 单次请求耗时 20s，但到达速率 0.45 req/s
   └─ 稳态并发数 ≈ 0.45 × 20 ≈ 9 … 实测堆积 76（因客户端 504 后重试放大）

3. 76 个并发请求各自持有：
   ├─ 一个 *sql.Rows + prepared statement
   ├─ 中间结果对象（Go 堆）
   └─ auditMiddleware 的 access_log 写入事务（access_log 已 275,561 行）

4. 堆分配速率远超 GC 回收能力
   └─ force gc 连续 3 分钟无法完成
   └─ finalizer wait 3 minutes / cleanup wait 3 minutes
   └─ Go 运行时进入 GC 抖动，CPU 全部烧在 GC 与查询上

5. 服务变慢 → 更多超时 → 更多重试 → 回到步骤 2
   └─ CPUQuota=200% 被打满，98.06% 调度周期被限流
   └─ 整个 cgroup（含 /__dash 管理台）一起变慢
```

**结论：这是一个"无背压 + N+1 + 无并发上限"的三重叠加缺陷。
请求量小并不代表安全——恰恰因为单请求够慢，才导致并发堆积失控。**

### 3.4 为什么 `/event` 正常而 `/beacon` 超时

| 端点 | 是否经过 `CommandQueue.TakeFor` | 结果 |
|---|---|---|
| `POST /event` | 否 | **100% 返回 200** |
| `POST /beacon`（触发 `registerC2`） | 是 | **98.2% 返回 504** |

`/event` 不碰指令队列，绕过了缺陷路径；`/beacon` 必然进入。这是定位的决定性对照。

## 6. 企业级修复方案（需源码）

### 6.1 P0 — 消除 N+1（治本）

**`panel_query.go:77` `ListDevices()`**

```go
// ❌ 当前：每台设备额外一次或多次查询
for _, d := range devices {
    d.StageProgress = ClientStageProgress(d.IP)   // 1956 次往返
    d.Profile      = Profile(d.IP)                // 另一次
    d.WalletMeta   = walletsMeta(d.IP)            // 又一次
}

// ✅ 改造：一次批量查询 + 内存关联
func ListDevices(ctx context.Context) ([]Device, error) {
    devices, err := deviceRepo.ListAll(ctx)   // 单次查询
    if err != nil { return nil, err }

    ips := extractIPs(devices)                 // 一次收集
    // 批量预取，用 IN / 临时表 / JOIN，查询次数固定为 O(1)
    stages, err := stageRepo.BatchByIPs(ctx, ips)
    if err != nil { return nil, err }
    profiles, err := profileRepo.BatchByIPs(ctx, ips)
    if err != nil { return nil, err }

    indexBy(stages, devices)                  // 内存 O(N) join
    indexBy(profiles, devices)
    return devices, nil
}
```

**要点**：SQL 查询次数从 **O(N) 变为 O(1)**；内存 join 为 O(N) 且无 I/O。

**验收**：1956 台设备下 `ListDevices()` P99 < 20 ms（当前约 20 s，提升 1000 倍）。

### 6.2 P0 — 引入并发上限（止血关键）

**`command_queue.go` `TakeFor` / `expandCands`**

```go
var expandSem = make(chan struct{}, 16)   // 硬上限 16 并发

func (q *CommandQueue) expandCands(ctx context.Context, ...) ([]Cand, error) {
    select {
    case expandSem <- struct{}{}:
        defer func() { <-expandSem }()
    case <-ctx.Done():
        return nil, ctx.Err()             // 快速失败，不堆积
    case <-time.After(2 * time.Second):
        return nil, ErrExpandBusy          // 背压：宁可 503 也不堆积
    }
    ...
}
```

**原则：宁可快速失败（503 + `Retry-After`），也不允许无上限堆积。**
堆积 76 个请求对系统是净损失——每个都在消耗内存和 CPU 却产不出结果。

### 6.3 P1 — 候选集缓存（消除重复计算）

`expandCands` 的候选集在秒级窗口内几乎不变，无需每次全量重算。

```go
type CandCache struct {
    mu    sync.RWMutex
    items []Cand
    expire time.Time
}

func (c *CandCache) Get(ctx context.Context) ([]Cand, error) {
    c.mu.RLock()
    if time.Now().Before(c.expire) { d := c.items; c.mu.RUnlock(); return d, nil }
    c.mu.RUnlock()

    // 缓存未命中时用 singleflight 合并并发回源
    v, err, _ := c.sf.Do("cands", func() (any, error) {
        cands, err := expandCandsRaw(ctx)
        if err != nil { return nil, err }
        c.mu.Lock(); c.items, c.expire = cands, time.Now().Add(2*time.Second); c.mu.Unlock()
        return cands, nil
    })
    ...
}
```

**收益**：即使 N+1 未完全修好，2 秒 TTL 也能把 QPS 降低 2 个数量级。
